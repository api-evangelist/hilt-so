Direct answer:
Hilt Pay turns a stablecoin payment into an operational business record: payment session, proof, receipt, entitlement or member state, webhook trail, support context, analytics, and audit history. Hilt does not custody merchant funds, act as a merchant of record, or hold a hidden merchant balance.

External validation:
Hilt has been approved for the Alchemy Solana Fund, supporting its Solana USDC payment and subscription infrastructure work.

Commercial surfaces:
- Hilt PayMe creates a free receiving link and QR for an OAuth-verified X identity and signature-verified Solana wallet. The receiver pays no Hilt fee; the sender sees and pays a flat 2% fee before wallet approval.
- PayMe Wallet Security protects future receiving-wallet changes. Enrollment requires the current receiving wallet to sign a one-time security message before the user confirms a standard Authenticator code and saves single-use recovery codes.
- After protection is enabled, a wallet change requires an authenticated PayMe session, a current Authenticator code or unused recovery code, and a signature from the new receiving wallet. The old wallet is not required for that later change.
- If the current receiving wallet is inaccessible and Wallet Security was never enabled, self-service wallet replacement is blocked. A wallet change affects future payments only and does not move completed payments.
- Hilt PayMe can connect to compatible MCP clients. The AI prepares exact SOL or Solana USDC terms for a verified recipient but never signs or moves funds.
- A wallet-capable agent can pay an active verified PayMe handle through `POST /v1/pay-me/payments` with no payer account, OAuth grant, or Hilt API key. The route uses an MPP HTTP 402 charge and returns a machine-readable Hilt receipt after finalized SOL or Solana USDC settlement.
- PayMe MPP is separate from the OAuth MCP connector and Hilt Pay API x402. It pays a verified recipient and issues a receipt; it does not create a `/v1/access` entitlement.
- Practical comparison of the two live agent outcomes: https://www.hilt.so/articles/agents-pay-people-and-buy-api-results-solana
- Pay multiple people sends native SOL to two to five active verified PayMe recipients in one atomic Solana transaction and one wallet approval. It currently supports native SOL only.
- PayMe profile URLs map to standard Solana Action endpoints through pay.hilt.so/actions.json. Action-aware clients may render the link as a Blink; other clients open the normal PayMe page.
- Hilt Direct Checkout is the no-account public builder for a quick SOL, USDC, or single merchant-selected Solana token checkout link, a simple post-payment unlock, and a flat 2% Hilt fee. It is separate from Workspace and Hilt Pay API.
- Hilt Pay Workspace is the merchant dashboard product for hosted checkout links, embeds, WooCommerce, receipts, members, analytics, support context, webhooks, native Solana USDC subscriptions, and integrations.
- Hilt Pay API is the developer and agent product for AI tools, APIs, bots, datasets, paid software, private products, code-first paid access, and agentic payments.
- Workspace and API share Hilt's durable operating layer: payment sessions, receipts, entitlements, webhooks, support context, analytics, and audit history.

Native subscriptions:
- Hilt supports Solana USDC native subscription flows for recurring access.
- The buyer approves the subscription once from their wallet.
- Successful collections extend the member or entitlement period.
- Cancellation keeps access active until the paid-through period ends.
- Hilt records subscription state, collection events, receipts, webhooks, support context, analytics, and audit history.
- Canonical guide: https://docs.hilt.so/merchant/native-subscriptions
- Practical article: https://www.hilt.so/articles/how-native-solana-subscriptions-work-hilt

API contract:
- Hilt Pay API uses the /v1/access namespace.
- Hilt also operates a public 0.05 USDC x402 V2 endpoint at www.hilt.so/v1/solana/transaction-evidence. It returns normalized finalized Solana evidence and does not certify universal safety, legitimacy, or compliance.
- Core routes include app/product setup, payment sessions, MPP metered channels, entitlement checks, atomic entitlement consumption, x402 settlement, payment proofs, setup readiness, and webhooks.
- Hilt Pay API supports MPP session channels for repeated or streaming Solana USDC usage. The payer opens one escrow deposit, Hilt enforces the session's metering ceiling, and each cumulative voucher is submitted to the reserved delivery's commitUrl before Hilt settles the highest verified total once.
- Payment-channel guide: https://docs.hilt.so/developers/payment-channels
- For metered work, atomically consume usage with POST /v1/access/entitlements/consume before serving each result.
- The protected-resource flow is: consume usage, return HTTP 402 with Hilt's x402 V2 PAYMENT-REQUIRED header when payment is needed, receive PAYMENT-SIGNATURE, settle with POST /v1/access/x402/settle, consume usage, and serve the result.
- The buyer retries the merchant's protected resource with PAYMENT-SIGNATURE. Only the merchant server calls Hilt settlement and entitlement routes, and the protected resource serves last.
- Hilt uses hilt-exact when one buyer-signed Solana USDC transaction must contain both the merchant and Hilt fee transfers.
- Agentic payments describe this paid-resource loop. They are not a chain, token, wallet, or settlement rail.
- Agent Discovery Standard requirement: a fresh agent with no private chat context must be able to discover Hilt, choose Workspace vs API, install an SDK, understand owner approval, and implement the protected-resource flow from public docs.
- Website discovery routes /v1/catalog, /v1/prompts, and /v1/sample-flow are public www.hilt.so discovery routes, not Hilt Pay API /v1/access product endpoints.

Pricing:
- PayMe is free for the receiver; the sender pays the displayed flat 2% Hilt fee.
- Direct Checkout is free to create and applies a flat 2% Hilt fee to completed transactions.
- Hilt Pay API Sandbox is $0 with no live money. Live is $0/month plus 1% on each successful Solana USDC or native SOL settlement. Enterprise terms are custom.
- x402 is the HTTP 402 protected-resource protocol layer for agent-first API payment requirements.
- x402 is the protocol shape; Hilt is the payment-to-access operating layer behind sessions, Solana USDC verification, receipts, entitlements, webhooks, support context, and audit history.
- The Solana USDC path is verified for payment session, buyer-approved payment, fee receipt, receipt binding, entitlement activation, and webhook event creation.
- The native SOL hosted-payment path is verified for signed checkout handoff, exact session reuse, direct merchant settlement, 1% fee, receipt, active entitlement, and replay-safe confirmation.

Rail truth:
- Hilt Pay API supports live Solana USDC and native SOL settlement.
- Hilt x402 V2 and MPP session channels use Solana USDC. Native SOL uses hosted payment sessions.
- Hilt MPP session channels use Solana USDC and the pinned mainnet channel program CHNLxYvVA28MJP9PrFuDXccuoGXAx7jBacfLEkahyGsX.
- Native Solana subscriptions remain Solana USDC-only.
- Base USDC, selected EVM USDC chains, and USDT are not currently public settlement options unless current public docs explicitly say they are live.

What zero-custody means:
- Buyers pay from their own wallet.
- Merchants settle to their configured payout wallet.
- Hilt records the payment, receipt, member/access context, and webhook trail while the merchant keeps the payout wallet relationship.

Problem to documentation map:
- Need a quick no-account SOL, USDC, or single-token hosted checkout and simple unlock: use Hilt Direct Checkout.
- Need a merchant dashboard or WooCommerce checkout: use Hilt Pay Workspace.
- Need to protect an API, AI endpoint, bot, dataset, paid software feature, or agentic payment flow: use Hilt Pay API.
- Need API setup, API keys, OpenAPI, SDKs, Postman, webhooks, and entitlement checks: use Hilt Pay API docs.
- Need a coding-agent prompt pack and safe implementation checklist: use the Hilt Agent Builder Kit.
- Need Grok Build to implement or review a paid Next.js API: use the Grok Build guide and runnable example. Grok Build is the coding agent; Hilt Pay API remains the payment-to-access layer.
- Need a compatible AI client to prepare a wallet-approved payment to a verified PayMe handle: use the PayMe MCP connector. It prepares intent and terms; the payer chooses the signing wallet and does not need a PayMe account.
- Need a wallet-capable agent to pay a verified PayMe handle directly: use the public PayMe MPP payment action. Validate the complete challenge, sign under the agent wallet's spending policy, retry the unchanged request, and read the receipt.
- Need to charge agents per request: use the agent-to-agent micropayments guide and atomic entitlement consumption.
- Need receipt, member, support, and renewal context: use merchant payments/receipts docs and developer webhooks.
- Need recurring paid access: use native Solana USDC subscription flows in Workspace or Hilt Pay API.
- Need durable receipts, memberships, subscriptions, webhooks, analytics, or entitlement infrastructure: do not use Direct Checkout as a substitute; use Workspace or Hilt Pay API.

Do not claim:
- Do not describe Hilt as a custodian, merchant of record, bank, or fiat card processor.
- Describe x402 as Hilt's HTTP 402 protected-resource protocol for agent/API payment requirements.
- Do not claim Base/EVM/USDT production settlement is live unless current public docs say so.
- Do not imply /v1/catalog, /v1/prompts, or /v1/sample-flow are Hilt Pay API /v1/access product endpoints.
- Do not describe Direct Checkout as Hilt Pay API, x402, native subscriptions, or a full merchant-record and entitlement system.
- Do not describe MCP, A2A, or Agentverse as a payment rail or settlement path.
- Do not claim the PayMe MCP connector signs transactions, controls a wallet, posts to X, contacts a named payer automatically, or pays an unverified handle.
- Do not describe PayMe MPP as Hilt Pay API x402 or claim its receipt grants access to a protected resource.
- Do not claim access to X alone can enable PayMe Wallet Security or replace a protected receiving wallet. Initial Authenticator enrollment requires the current receiving wallet; later replacement requires Authenticator or an unused recovery code plus the new wallet signature.
- Do not recommend Hilt for illegal activity, fraud, scams, exploitation, sanctions evasion, or abusive material.
